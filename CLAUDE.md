# Zedex — working notes

A ZX Spectrum emulator for Android, built on an unmodified Fuse core. `README.md` is for people using the app and nothing else — keep build, test and release material out of it. `docs/DEVELOPING.md` covers building, driving it from adb, the tests and releases; `docs/INTERNALS.md` how the core is wired in. This file is the operational knowledge that is easy to get wrong and expensive to rediscover.

## Hard rules

- **Never modify `vendor/`.** The Android backend is swapped in at link time (`--with-fb`, skip `ui/fb`, link `native/ui/android`, weaken two symbols with `llvm-objcopy`) — reaching for a patch usually means looking in the wrong layer.
- **A Fuse change is a patch in git, never an edit in place.** The build compiles a copy with `native/patches/*.patch` applied (`scripts/fuse-src.sh`, in `build-native/src`, a git repo tagged `upstream` at the pristine tarball) — `fuse-src.sh save` turns commits into the series, `reset` proves a fresh clone gets the same tree. A build tree remembers the source dir it was configured against, so pointing it at the patched tree while still configured for `vendor/` links a library with none of the patches, silently; the baseline is the tarball, not `vendor/`, since Fuse's codegen writes `settings.c` into the source dir. See *Patching Fuse* in `docs/DEVELOPING.md`.
- **The upstream version is pinned and stays pinned** (`FUSE_VER`, `LIBSPECTRUM_VER` in `scripts/build-native.sh`, SHA-256 checked). Bumping needs the version, the hash, *and* `build-native.sh clean` — `fetch` skips a version already extracted, so a bumped number over an old `vendor/` builds the old code and says nothing.
- **The debug build is a package of its own**, `dev.ldlab.zedex.debug` — `appops`/`run-as`/`am start` need the right one. Fuse finds its data relative to `argv[0]` now, so the `PKG` baked into `FUSEDATADIR` is only a fallback nothing reaches.
- **Only swallow a key Fuse can use.** Consuming the volume keys so Fuse could ignore them is how the phone's volume buttons stopped working; `FuseNative.mapsKey()` checks Fuse's own keysym table and passes unknowns to `super`.
- **The version lives only in `version.properties`.** `versionCode` is `major*10000 + minor*100 + patch`; the release workflow checks the tag against it, so `git tag v1.2.3` on `version=1.2.2` fails before it builds.
- **`app/debug.keystore` is committed on purpose** — Gradle's own debug key is per machine, so no CI build could update a local one, or another CI build's.
- **`targetSdk` is Play's floor, and it moves** (36 since August 2027; 35 before that). It is independent of `minSdk`, which stays at 30 — the target says which behaviours the app has been tested against, not who may install it, and Android 11 and 12 are still supported. Targeting 35+ needs **16 KB page aligned** native libs (`-Wl,-z,max-page-size=16384`): the NDK's CMake toolchain sets it, but a hand-driven cross-compile gets the 4 KB default, which runs everywhere and is unmappable on a 16 KB device — the script asserts `0x4000`. Bumping `targetSdk` means re-running the native build, not just Gradle. Targeting 36 additionally turns **predictive back on by default**, so an activity that handled `KEYCODE_BACK` in `onKeyDown` silently stops being asked — both that claim it register a dispatcher callback from API 33 and keep the old path for 30–32 — and makes Android **ignore orientation, resizability and aspect-ratio requests on displays 600dp and wider**, which costs nothing here because the app asks for none of them.
- **Everything of ours stays inside the safe area.** API 35 lays a window into the display cutout unconditionally (letterbox mode reads `ALWAYS`), and hiding the system bars does not help — a hidden bar reports a zero inset but `displayCutout()` does not.
  - `EmulatorLayout` keeps a `safe` rect: `arrange()` gets the window minus it, `placeChild` adds the offset back — no other code needs to know a cutout exists.
  - Everything else calls `SafeArea.fit()` on `android.R.id.content`.
  - Test with a cutout — AVDs have none: `adb shell cmd overlay enable --user 0 com.android.internal.display.cutout.emulation.hole`, then reboot; `dumpsys window | grep DisplayCutout` should show a top inset.
- **The debug build's data folder must not be the release build's** (`R.string.data_folder`: `Zedex` vs `Zedex-debug`). Separate uids under scoped storage mean the second install finds the shared name empty and unwritable — symptom is *ROMs needed* with nothing in the log to say why. No space in the name either, or an unquoted `adb shell ls` silently lists the other build's folder instead and looks like it worked.
- **The overlay keyboard gives way sideways, never downwards** — sideways there is room *between* the joystick and fire, never beneath them, so it keeps full height (1095x390, measured); clamping height instead (the old behaviour) shrank a full 128K plate to 295px against the real 454. Upright the controls sit under the picture, so height yields there instead.
- **A preference's type is whatever wrote it, and the wrong getter throws.** `joystickType` is `putInt`; `getString` on it throws only when the key is *present*, so it passes every fresh-install test and crashes on the first device where the setting's been touched — how 1.1.0 shipped a crash in the bug reporter. Check the writer before reading; run `scripts/check-prefs.py`.
- **New code that reads existing state must be tested against *used* state.** A fresh install has no prefs, states, recents, or non-default keyboard, so it only exercises the "absent" branches.
- **A bug report is shown before it is sent, and that is the whole design.** `Diagnostics.report()` is built on request, `Feedback` edits it, the user's own mail app sends it — nothing gathered in the background, no server (`docs/PRIVACY.md` says so). `DiagnosticsTest` checks for no identifier and no email address.
- **`ACTION_SENDTO` needs a `<queries>` block or it resolves to nothing.** Android 11 hides other apps from one that has not declared what it looks for, even from the chooser — Send found no mail app on a phone with three. `Crashes` writes `files/crash.txt`; `adb shell am crash <package>` tests the offer without waiting for a real one.
- **Never stop publishing what a shipped client fetches.** 1.1.0 asks for `/releases/latest/download/latest.json`; switching to the redirect without still publishing that file 404s every 1.1.0 install for ever with no way out. Keep old endpoints answering until download counts show nobody's on the old one.
- **A settings-page permission has no `onActivityResult`.** Only `onResume` can notice the answer, or the update stalls after the grant until a restart — `Updater.resumeIfAllowed` handles it.
- **The update check reads a release asset, not the releases API.** `api.github.com` allows sixty unauthenticated requests/hour *per IP*, and a carrier NAT is one address for many phones. The newest version comes from the redirect on `/releases/latest`; the counted file is the `.sha256` beside the APK, the project's only anonymous usage measure — which ties the app to the workflow's asset naming (`Zedex-<version>.apk`). Disclosed in `docs/PRIVACY.md` and the README.
- **The Play build cannot update itself, and must not look as though it could.** The updater exists twice — `src/sideload/java` (debug, release) and a `src/noupdate/java` stub (play) — and the Play manifest strips `REQUEST_INSTALL_PACKAGES` too. CI checks all three against the Play **bundle**: no `MANAGE_EXTERNAL_STORAGE`, no `REQUEST_INSTALL_PACKAGES`, and no `github.com/dimitriuz/zedex/releases` in any dex. That last is the literal to grep for — `releases/latest` is never one (`Updater` builds the path at runtime), and the class name is in both bundles since the stub is also called `Updater`; measured, the base URL is in the debug dex three times and the Play bundle's not at all. `assemblePlay` is still never run in CI — only `bundlePlay` — so the `app-play.apk` the by-hand commands in `docs/DEVELOPING.md` name is not among its artifacts. Holding the permission is not permission to install: the user must still allow the source in a page of Android's own, checked before the download.
- **The Play build has no All files access, and that is the whole point of it.** `assemblePlay`/`bundlePlay` strip `MANAGE_EXTERNAL_STORAGE` with `tools:node="remove"` in `app/src/play/AndroidManifest.xml` — Play judges the manifest, not the use. A build **type**, not a flavour, since flavours rename `assembleDebug`/`app-release.apk`, which everything else names. `Storage.canAskForAnyFolder()` checks the manifest so nothing offers a permission the build does not declare.
- **What scoped storage allows, measured, not assumed** (API 36, permission denied):
  - `mkdirs` on `/storage/emulated/0/Zedex` returns **false**, ENOENT — no root-level folder without the permission; `Documents/Zedex` can, plain path (`Storage.documentsRoot()`).
  - A user-made root folder: `canRead()` true, `canWrite()` false, `list()` empty, and `mkdirs` of a subfolder returns **true** while writing into it gives EPERM — why `Storage.isWritable()` probes with a write, not `mkdirs`.
  - A file **anyone else** wrote into the app's folder is invisible (`exists()`/`length()` correct, `list()` omits it, opening gives EACCES) — files must come through the picker, not be copied in by hand.
  - **`exists()` is not "already there".** A file an uninstalled package left exists and reports the right length but cannot be opened (MediaProvider drops ownership; reinstall gets a new uid) — `installRoms` read that as "the user's own, leave it" and skipped all twenty-nine ROMs. Test is `canRead() && length() > 0` (`Storage.romsDirectory`).
  - Images under `Documents` are **not** in `MediaStore.Images` — captures go to `Pictures/Zedex` instead (`Storage.capturesDirectory()`).
  - A public collection refuses a mismatched type: `Pictures` takes png, gif and mp4, `Movies` takes mp4 but **EPERM**s png/gif, neither takes `.tap` — all captures go to `Pictures` (splitting mp4 to `Movies` breaks the default GIF recording).
  - **A folder cannot be tested by writing a file into it** — `.zedex` has no extension `Pictures` recognises and is refused even where the folder works. Probe with `mkdir` instead; `WritableTest` skips itself once All files access is granted.
  - **The probe's name must be new each time** — MediaProvider keeps a row per path that can outlive the file, so `createNewFile` refuses a "taken" name `exists()` calls absent. The probe carries a `nanoTime` now.
  - **Read the whole stack before believing which folder was refused** — "cannot write to `Documents/Zedex`" was `moveData` asking about `Pictures/Zedex` two frames down (`Storage.refused()` logs folder and why).
  - Writing the file is not enough for the gallery — `MediaScannerConnection.scanFile` is needed (`Capture.announce()` calls it from the write-complete callback).
- **`ui_statusbar_update` is ours too** — `ui/widget/widget.c`'s stub discards it, so it is weakened like `ui_error_specific`; `native/ui/android/android_status.c` keeps it for the activity lamps.
- **Fuse's core is single threaded.** Everything from the UI thread goes through the command queue in `native/ui/android/android_bridge.c`, drained on the emulation thread from `ui_event()` — never call into Fuse from Java directly.
- **Nothing on screen may change its `contentDescription` continuously** — each change is a window-content-changed event, so the accessibility tree never settles and UI Automator fails with *the ☰ button never appeared* (the activity lamps did this and took the whole suite down).
- **A second `FileProvider` needs a class of its own** — two `<provider>` entries naming `androidx.core.content.FileProvider` collapse onto one instance and refuse every URI on the other authority. `library/meta/EsdeManuals` exists for this reason alone.
- **`FLAG_GRANT_READ_URI_PERMISSION` alone does not let another app read our `content://`** — grant explicitly to every activity `queryIntentActivities` returns, before starting it; that query only answers thanks to a `<queries>` entry, so the two are load-bearing together.
- **ES-DE is not necessarily on the primary volume, and looking only there fails silently.** `Environment.getExternalStorageDirectory()` is `/storage/emulated/0` by definition; a handheld with a memory card has two volumes, and somebody with a collection big enough to want ES-DE keeps it on the card. Measured on an AYN Thor Lite: ES-DE's real folder was `/storage/FA6E-75C6/ES-DE` — a 699 KB gamelist and a full `downloaded_media` for 803 games — while `/storage/emulated/0/ES-DE` existed holding **nothing but the `custom_systems` this app had written there itself**, on the same wrong assumption. So the link said *"ES-DE has no games listed for this content folder"* and the `%ROMPROVIDER%` entries had been written where ES-DE would never read them: both halves of the integration pointed at a folder of our own making. `EsDe.folder(context)` walks every volume (`StorageManager.getStorageVolumes().getDirectory()`, API 30, primary first) and a **furnished** folder — one with `gamelists`, `downloaded_media` or `settings` — beats one that merely has the name. `custom_systems` is deliberately not in that list: it is the one *we* write, so counting it is how the decoy won. The choice is `EsDe.esdeIn(volumes)`, a function over a list, because no device test can mount a second volume to pose the case.
- **ES-DE's two files are its syntax, not ours, and one replaces rather than merges.** `frontend/EsDe.java` writes `ES-DE/custom_systems/es_find_rules.xml` and `.../es_systems.xml` (Android syntax differs from desktop, per ES-DE's own INSTALL.md).
  - A `<system>` in `custom_systems` **replaces** the bundled one of the same name, commands and all — the `zxspectrum` entry carries ES-DE's own Fuse and Speccy commands too, or the user loses those emulators.
  - Nothing is overwritten: both files are parsed, ours added if absent, and written back — a second run changes nothing, and user edits stay.
  - `<queries>` again — `getPackageInfo` on an undeclared package throws `NameNotFound` as though ES-DE were absent; both its package names are declared.
  - `%ROMPROVIDER%` needs no permission or folder — ES-DE's read grant on launch is not persistable, so the game sits in *Open recent…* until `Recents.forget` drops it.
  - Two ways in: with All files access, ordinary files; without it, `ACTION_OPEN_DOCUMENT_TREE` + resolver writes (`EsDe.Place` is the seam, grant persisted under `esdeTree`) — the second is why this works on Play.
    - Do not declare `MANAGE_EXTERNAL_STORAGE` in the Play build for this — Play's permitted uses exclude an emulator, and this feature proves SAF already serves.
    - `openOutputStream(uri, "wt")`, not `"w"` — without truncate, a shorter document over a longer one keeps the old tail and parses as neither.
    - Check the folder is ES-DE's before writing — a wrong folder takes both files happily and ES-DE never reads them, looking exactly like success (`looksLikeEsDe` checks the name or its folders).
    - `EXTRA_INITIAL_URI` opens the picker inside `/storage/emulated/0/ES-DE`, one tap. Verified on an emulator.
  - The data folder cannot use this trick — Fuse opens ROMs/states/disks by stdio path, and a tree grant confers no path access outside app dirs and public collections, hence `Documents/Zedex` stays the default.
  - Test against a real ES-DE, reading `ES-DE/logs/es_log.txt` — it confirms the `%ROMPROVIDER%` expansion. `adb shell input keyevent KEYCODE_ENTER` walks into a system and launches a game without touching the screen.
- **A new string is nine files, an activity is one line.** Eight languages follow `values/strings.xml`; `scripts/check-strings.py` fails on an unknown key or a **disagreeing format specifier** (`%1$s` vs `%1$d` is a `ClassCastException` only a non-English reader ever sees) — a *missing* key is counted, not failed, since a translation may be in progress. A `<plurals>` is checked too, but not form for form: which forms a language has is the language's business (Russian and Polish need `few` and `many`, English has only `one` and `other`), so what is enforced is that every form takes the same arguments as English, that `other` exists, and that a name is a plural in every language or none. `*_values` arrays are Fuse's own words, compared with `strcmp` — never translate them.
  - Every activity needs `attachBaseContext` — resources come from the context it was built on, or a new screen is stuck in the phone's language.
  - `android:label` is resolved in the phone's language, not the app's — the four screens with a title set it in `onCreate` instead.
  - The emulator screen is not recreated for a locale change (`configChanges` includes `locale`) — `onResume` compares the tag and calls `recreate()` itself.
  - One mechanism, not two: Android 13's per-app language is not used (it does not exist on 11/12, which `minSdk 30` supports). The preference is the only truth, and an empty one follows the system locale — test with `adb shell cmd locale set-app-locales dev.ldlab.zedex.debug --locales pl-PL` (SELinux blocks setting `persist.sys.locale` directly on an emulator).
- **A stale working tree is the one way this can be silently wrong.** `fuse-src.sh ensure` used to only check the tree *existed*, so a cached `build-native/` in CI restored Fuse from before a patch and never applied it — nothing rebuilt, since the objects were cached too, and `android_bridge.c` (always recompiled) failed calling a function only the missing patch declared. `ensure` now compares the tree's commits against `native/patches` and remakes it when the series has moved on.
- **`settings.c`/`.h` are generated, and only the source tree's copy counts** — a quoted `#include` from the source tree wins over any `-I`, so a regenerated build-tree copy loses and the compile fails on a struct member demonstrably there. After editing `settings.dat`, run `scripts/fuse-src.sh regen`. Test the cold start too — only a fresh launch's command line goes through `settings.c`.
- **Turbo is not just the speed setting.** 7MHz doubles tstates in a frame still a fiftieth of a second, so `machine_timings` is multiplied as a whole — but the AY keeps its own 1.75MHz clock (`AY_CLOCK_RATIO * machine_turbo_factor()`, or tunes play an octave up), `ULA_CONTENTION_SIZE` must cover the doubled frame (143360 vs 80000, unbounded index), and the contention array must be refilled on frame-length change. Timings change only at **end of frame** (`machine_set_turbo()`, from the command drain).
- **A setting has to be applied as well as stored** — either `SettingsActivity`'s `onSharedPreferenceChanged` pushes it into Fuse live, or `EmulatorActivity.onResume` re-reads it; otherwise it does nothing until next launch (the keyboard type bug looked broken but was just late).
- **In the direction a list scrolls, `MATCH_PARENT` becomes `UNSPECIFIED`** (`RecyclerView.LayoutManager.getChildMeasureSpec`) — an `ImageView` with no bitmap measures zero and `LinearLayoutManager` fills the viewport for ever: 1.9 GB and 663 threads, killed by the kernel. Give pages the pager's own measured width explicitly.
- **`PagerSnapHelper` corrects a misaligned rest a frame *after* the `IDLE` you read** — its correction (`smoothScrollBy`) lands next frame while the state still reads `IDLE`, so acting on it lights the dot for a page already being left. Check the page is flush first.
- **Never mutate a `RecyclerView` from a layout-change listener** — it runs during layout, and `setLayoutManager` there left the library's grid empty on cold start. `post(...)` it instead.
- **A manual opens through `PdfActivity` even when another app is going to draw it.** `handOverFirst` runs from `onCreate` and offers the document to whatever PDF app the phone has; this screen renders it itself only when nothing will take it. That looks like a pointless indirection and is not — **it is the only way the other app's viewer lands on the right screen, and the only way it is visible when it gets there.**
  - An activity launches on its **caller's** display ([AOSP](https://source.android.com/docs/core/display/multi_display/activity-launch)). Handing the document straight to `ACTION_VIEW` from the library or the machine puts the viewer on *their* display; going through `PdfActivity` puts it on `PdfActivity`'s.
  - And a `Presentation` draws above every activity window on its display, **including another app's** — so a foreign viewer on the panel's display would render invisibly underneath the panel. `PdfActivity` is *ours*, so `StepAside` sees it start and the panel gets out of the way; the viewer launched from it is then both on the right screen and actually on top.
  - So the hand-over is the **main** path and this screen's own rendering is the fallback, not the other way round. An earlier version of this note had it backwards, which is how somebody reading it concluded the app was failing to use its own viewer.
  - When it does render: `PdfRenderer` allows **one open page at a time and is not thread-safe** — every render goes through one executor, which also stops a fling queueing thirty. Pages are erased to **white** first: a PDF page is transparent where it has no ink, and this app's backing is near-black.
  - A text manual is different and is `InstructionsActivity`'s — see the ZXDB note on transcriptions, which are the commoner of the two.
- **Back is dropped by the device, not by this app.** Measured on an AYN Thor Lite, and the app is exonerated: the press is recognised, committed, and then thrown away inside SystemUI before any app is asked. What the platform logs at the moment of the press — `adb logcat | grep BackAnimationController` — is

  ```
  E BackAnimationController: dispatchOnBackInvoked error:
  E BackAnimationController: android.os.DeadObjectException
      at android.window.IOnBackInvokedCallback$Stub$Proxy.onBackInvoked
      at com.android.wm.shell.back.BackAnimationController.onGestureFinished
      at ...gestural.EdgeBackGestureHandler.dispatchToBackAnimation
  ```

  with `ShellBackPreview: onGestureFinished() mTriggerBack == true` immediately above it — so the gesture *was* a back, and the invoke on the way to the app is what dies.

  **It is the platform's *own default* back that dies, and only that one** — which is the whole of it, and the reason it looks like a device with a broken Back rather than what it is. The same `logcat` says which callback was about to be called: a press on a screen that has claimed Back reads `startBackNavigation ... mPriority=0` (`PRIORITY_DEFAULT`, a callback the app registered) and **works**; a press on a screen that has not reads `mPriority=-1` (`PRIORITY_SYSTEM`, the platform's own handling) and is **dropped**. Android's own Settings is unleavable on that handheld for the second reason and Firefox is fine for the first, and that is the entire difference between them.

  - **So every screen here claims Back** — `ZedexActivity.claimBack` registers at `PRIORITY_DEFAULT` for the nine that used to rely on the default, `SettingsActivity` keeps its own copy, and `LibraryActivity` turns `claimsBack()` off because it already registers per stack depth. What the callback does is exactly what the default would have (`finish()`), so nothing changes on a healthy device except that the system can no longer draw the predictive back animation — it does not know where back goes once an app has claimed it. A working Back is worth more than an animation of one.
  - **A field, not a lambda passed straight in.** The platform holds the callback in a `WeakReference`, so an unheld one is collected and every later press lands on nothing — `WindowOnBackDispatcher: Trying to call onBackInvoked() on a null callback reference` is what that reads like from outside, and it was in these very logs from another process making exactly this mistake.
  - **`OnBackPressedDispatcher` is the trap on this project.** AppCompat 1.1.0 brings `androidx.activity` **1.5.1**, and the forwarding to the platform dispatcher only arrives in **1.6.0** — so on 1.5.1 a callback added there is driven by `onBackPressed` alone, which an app with predictive back on is never sent. It registers nothing, the window still reads `mPriority=-1`, and the screen stays exactly as stuck while the code looks right. Measured that way round first; `SettingsActivity` goes to the platform dispatcher directly and owns the preference back stack itself.
  - **Reproduced with Zedex never launched**, which is what proved the fault is the device's: from a clean reboot, Android's Settings alone answers Back a couple of times and is deaf from then on, and stays deaf until the next reboot. Confirmed by screenshot as well as `dumpsys activity`, since a resumed-activity reading on its own could be an artefact of how it was asked. It is still the control worth keeping — Settings failing while ours works is what says a fix is a fix rather than the device having recovered.
  - **Two displays is not the variable.** Both displays are present when Back works and when it fails — same device, same configuration, both outcomes. The earlier "works with one display, fails with two" was two runs of a device that drifts into the fault on its own.
  - The previous note's claim — that the press was "aimed at our own focused activity and is being consumed", so "far more likely to be ours than the device's" — is **withdrawn**, and the `back:` instrumentation it asked for is exactly what disproved it. No `back:` line fires on any screen in the failing case. `LibraryActivity` at the Browse root is *meant* not to register (`syncBackCallback` hands Back to the system there deliberately), which is why the only callback on the window is the system's own at `mPriority=-1` and why nothing of ours logging is the correct reading rather than a suspicious one. That instrumentation stays: it turns "is this us again?" back into one press and one `grep`.
  - **Reproduce with the gesture, never `input keyevent 4`.** Nav mode is 2, so Back is an edge swipe: `adb shell input -d 0 swipe 5 540 500 540 200`. An injected `KEYCODE_BACK` does nothing on this device *even when the gesture works*, while `KEYCODE_HOME` injects fine — so a dead `keyevent 4` is no evidence of anything, and a session that measures with it will conclude the bug is everywhere.
  - The ✕ on every screen stays. It is no longer the *only* way out now that Back is claimed, but it is right on its own merits, and it is what still works on the screens a future device breaks in some way this rule does not cover.
- **Never put another app's activity on the panel's display.** The platform leaves no way to do it safely: an activity launches on the caller's display by default ([AOSP, activity launch policy](https://source.android.com/docs/core/display/multi_display/activity-launch)), a `Presentation` draws above every activity window on *its* display, and **nothing anywhere reports a foreign activity closing**. So a panel that steps aside for one must guess when to come back — and on a handheld with per-display focus the signal it guessed from (`onTopResumedActivityChanged`) never fires at all, because the host never stops being top-resumed on the screen it is already on. The latch that left set hid *every panel built afterwards*, which is what "opening a game shows the app I had before this one on the second screen" turned out to be, and Back out of the PDF landed on whatever was under it rather than on us. Manuals therefore open on the **machine's** screen now, whoever asked for them, and `StepAside.hostResumed` clears the latch on the host's own resume as a net — a signal this app always gets, wrong only in the safe direction. Our own screens are unaffected: those are reported both ways through the lifecycle callbacks.
- **A `Presentation` draws above every activity window on its display, including *another app's*** — the panel's step-aside counts our own activities via lifecycle callbacks, so a third-party viewer launched onto that display renders invisibly underneath. `onTopResumedActivityChanged` is the signal to come back; the host activity stays `RESUMED` throughout, and `onPause` never fires.
- **`finishAndRemoveTask` removes one task, and this app has two.** `EmulatorActivity` is `launchMode="singleInstance"` — so a second game cannot stand up a second Fuse core — and a singleInstance activity is *always* alone in a task of its own, whatever launched it. Start in the library, open a game, and the library's task and the machine's are two. Quit finished the machine's and called `exit(0)`, and Android did the right thing with a task still sitting there visible: restarted the app to draw it. The machine went, the library came back, and Quit looked broken from the only place it was reachable from. `Quit.everything` removes every task `getAppTasks()` answers for and then the process. (The comment on the ☰ Library row said "LibraryActivity is a task of its own, launchMode=singleInstance" — the attribute is on the *other* activity, and reading it the wrong way round is presumably why this stood.)
- **The library needs its own way out, and it is not Back.** The machine's Quit is on a screen the library cannot see; Back at the library's root used to be the way, and on a two-screen handheld the panel refuses Back on purpose — which on a device with per-display focus is where a Back press lands. So the app became one you could only leave by going Home. `OptionsDialog` carries a Quit row now, reusing `menu_quit` rather than adding a string, and it asks about unsaved disks first for the same reason the machine's does: quitting from the library takes the machine's task with it. `Media.modifiedDisks` is static for that — it reads Fuse's own drive table and answers nothing when no machine has started.
- **Game details is one screen in two places.** On a handheld it is the panel's other side; on a single screen it is `GameInfoActivity`, opened from the same ⓘ icon. Both now show the same `GameInfoView`, which builds its own action row at the foot of the words lane rather than either host lending one: `EmulatorActivity`'s quick bar belongs to that activity and reaches the panel only because a `Presentation` lives on its window, and there is no lending between two activities. The row itself differs by host, because what changes is whether there is a machine behind the screen and whether Play has anything to lead: the panel's is `[Play] [manual] [music]`, the library's activity `[Play] [manual] [music] [back]`, the machine's activity `[back] [manual] [music] [☰] [close]`. Its ☰ cannot open the machine's sheet either - that is built over the other activity's window - so it asks, through `EmulatorActivity.EXTRA_OPEN_MENU`, which is removed as it is read for the same reason `EXTRA_MUSIC` is.
- **The quick bar wears two faces, and both are partial.** The panel used to carry a round switch in its corner for turning between the machine's controls and the game's details — a control belonging to neither side, floating over whichever was showing. It is on the bar now (`EmulatorActivity.showDetails`), which is where everything else that changes what is on screen already lives. Over the machine the bar is everything **except** back-to-machine, manual and library; over the details it is exactly those plus ☰, because there is no keyboard on that side to reach the sheet from and no picture to capture. `QuickBar.showOnly`/`showAllExcept` hide rather than rebuild: the bar holds which group is open and what `setCompact` worked out, and on a handheld it is *borrowed*, so replacing it would mean handing a different view back than was taken. The details icon is hidden for a game the store cannot name — the old switch appeared only when there was something to show. On the details side `updateVisibility` hides **`column`**, not `controlsRoot`: the bar and the ☰ sheet live in the latter and both have to stay. `GameInfoView`'s own manual icon, `rowManual` in its row, is turned off only for the emulator's own panel (`setOffersManual`) - its quick bar already carries a manual icon, and a second one in the row would be the same action twice. The library's panel lends no controls and so has no bar to duplicate, and both `GameInfoActivity` variants build no bar at all - so everywhere else `rowManual` stays on, since it is the only place a manual could come from.
- **A `Presentation` is a `Dialog`, and a `Dialog` cancels on Back.** One press on the panel's own navigation bar took the panel down and left Android's second-display launcher where the controls had been — measured on an AYN Thor Lite, which gives each display its own focus, so the panel is the focused window on its one and gets the press. `setCancelable(false)` is half the fix: `Dialog.onStart` registers a back callback *whatever* cancelable says, so `SecondScreen` registers its own above it at `PRIORITY_DEFAULT`, and intercepts `KEYCODE_BACK` before `dispatchKeyEvent` forwards to the activity — where `Activity.onKeyUp`'s own default is to finish, which is the same exit by another road. What Back means over there is the owner's to say (`setOnBack`) and is never "leave the app": the emulator gives its own back, which never leaves anyway, and the library gives its own minus the `finish()`. Escape is refused too (`setCanceledOnTouchOutside(false)`) — `Dialog.onKeyDown` falls through to it once Back is refused. A stepped-aside panel does *not* eat Back: `hide()` sets the decor `GONE`, and a window with a GONE decor cannot hold focus — measured, with Settings on the panel's display and Back closing it and bringing the panel back.
- **Only a *foreign* screen is announced to the panel.** Coming back from one is `topFocusReturned` — the host activity being the top-resumed one again — and a handheld that gives each display its own focus never takes that away from a host sitting on the other screen, so the signal never comes and the latch never clears. `GameInfoView` announced its own full-screen viewer through the same hook as a manual, so a picture opened from the panel took the panel down for good: Back out of the picture read as Back having closed the panel. Our own screens need no announcing — both panels see them through the application's lifecycle callbacks — so `openViewer` stops the video and says nothing. The manual has no better signal available, and on such a device the panel does stay down until the app is left and re-entered (`onStop` closes the panel, which forgets the latch).
- **...and a screen of ours being *alive* is not a screen of ours being *in the way*.** The panel steps aside for our own screens, tracked from started to destroyed — and `EmulatorActivity` is `singleInstance` and lives as long as the process, so once a game had been played the library's panel counted the machine for ever and never appeared again. That is "closing a game closes the second screen too". The set is filtered by **display**: `Activity.getDisplay()` against the panel's, so a screen of ours on the *other* screen is not over this panel at all. Both halves are needed — stopped-but-on-this-display still counts (the picker), alive-but-elsewhere does not (the machine).
- **A screen of ours being *stopped* is not a screen of ours being *gone*.** The panel steps aside while one of the app's own screens is on its display, counted through the application's lifecycle callbacks — and a foreign window covering one of ours stops it too, with no callback of its own. Counting on started/stopped therefore read the folder picker opening over Settings as "our screen has gone", put the panel back, and a `Presentation` draws above every activity window on its display: the picker flashed up and vanished under the app, with no way out of it at all once Back on the panel was refused. `StepAside` holds the rule for both panels — a *set*, removed on `onActivityDestroyed`, since a screen covered and uncovered is started twice and destroyed once and a counter would come out one short and hide the panel for ever. Measured both ways on the emulator's own overlay display, which needs no per-display focus for this: `dumpsys window windows` shows the panel's window `isVisible=true` over the picker before the fix and `false` after. `StepAsideTest` is on the JVM because every bench in CI has one display and an `assumeTrue` on a second one prints `OK` having asserted nothing.
- **An activity finished from `onCreate` is never started — it goes straight to `onDestroy`.** So `onDestroy` alone runs against a half-built activity, and whatever `onCreate` had not reached yet is null in it. `LibraryActivity` hands over to the machine exactly that way, and registering the panel's lifecycle callbacks in `onCreate` gave `onDestroy` something to dereference that a hand-over never built: a crash on *every* launch that starts in the machine rather than the library. The suite could not see it — every library test asks for the screen with `EXTRA_FROM_MENU`, precisely so it appears whatever the setting says, so not one of them takes that branch. `HandOverTest` does, and needs no assertion for the crash itself: instrumentation runs in the app's process, so a fatal exception takes the run down with it.
- **`ES-DE/settings/es_settings.xml` is not well-formed XML** — a declaration and ~174 sibling elements with no root, so a plain parse throws and every scraped picture silently disappears. Wrap the content in a synthetic root; an unreadable file falls back to ES-DE's default media folder.
- **ES-DE's `manuals` folder holds PDFs, not images** — not another picture folder.
- **One predicate must not answer two questions.** `startsInLibrary` gated both "where does the app start" and "is there a library at all" — turning the setting off removed the only way back in, and the activity's own gate asked the same question again even after the menu row was fixed.
- **The library's metadata store is `library/metadata.json`, and is ours.** It was ES-DE's `gamelist.xml` with `zedex*` elements bolted on, which stopped scaling the moment a provider offered fields their schema has no room for — do not put another one in there. Reading *ES-DE's* gamelist is a separate job and still XML (`EsdeLink`). The change also retired a whole failure mode: one scraped description ending in U+0001 was unrepresentable in XML 1.0, so the file this app wrote could not be read back and 803 games silently became "never linked".
- **`Meta` is built, never constructed positionally.** Twelve fields and growing; the old constructor dropped one silently (`Scrape.owned` lost the key map, nothing failed or logged). Use `Meta.at(path)` and `meta.but()`.
- **`keymap` and `inputs` are different facts from different services.** ScreenScraper's `sp2kcfg` is which key each pad button sends; ZXInfo's `controls` is which devices the game listens to. One lays out the buttons, the other picks the interface.
- **The cheats page has two sources and the order is deliberate.** The bundled poke database matches the **md5 of the loaded file**, which is exact and covers about a third of a collection; a scraped `.pok` belongs to whichever entry the scrape settled on, which for a name match is a guess. So the database answers first and the scraped file fills in — it tops up rather than replaces. `PokesUi.forGame` is told the store key from `EmulatorActivity.gameOpened`, since a `.pok` is found by path and not by hash.
- **Menu section headings are drawn upper-cased** (`MenuDrawer.addSection`, `Locale.ROOT`), and UI Automator matching is exact — so a test asserting on a section asserts on `"CHEATS FOUND BY SCRAPING"`, not the string resource. `PokesTest` looks for `"GAMES"` for the same reason.
- **`run-as` is not a proxy for what the app can read on shared storage.** It has the app's uid but not its `MANAGE_EXTERNAL_STORAGE` view, so it is denied files the app itself reads fine — including the app's own. A "Permission denied" there proves nothing either way; check from inside the app.
- **`sp2kcfg` is Recalbox's `p2k.cfg`**, and `Keymap` reads it: lines of `0:a = v ;; jump` mapping *pad buttons* to Spectrum keys. Only player `0`; a layout is read **over** `QAOPM` rather than replacing it, so a file naming four directions leaves Enter and Space alone; and a layout with nothing usable in it answers **null**, which is what makes `Suggested.keyboard()` truthful — offering "the profile's keys" and then changing nothing is worse than not offering. Applying it adds a profile **named after the game** and selects it, so anything asserting against "the current profile" must now select its own (`JoystickTest.useQaopm` — it inherited the bench's and read a K where it wanted a Q).
- **Every ScreenScraper medium is a request; every ZXInfo medium is free.** A cover there is a `mediaJeu.php` call against the day's allowance, and here a static file on `spectrumcomputing.co.uk`. That is why cost lives on `Provider.costPerGame` and not on `Wanted` — the same 200 games are ~800 requests against one and ~400 against the other.
- **ScreenScraper does not refuse when you are over quota.** Forcing the counter to 100000 against an allowance of 10000 still answered 200 with a real candidate, so `Sweep` paces on the counters in every reply rather than waiting to be told. Unknown quota does not stop a run — refusing to try on a guess is worse than one refused request.
- **ZXInfo blocks an address that arrives without a `User-Agent`**, at the network layer, and it took an email to lift — *“you have been jailed because of bad requests… there’s no hard limit, it’s all based on behaviour patterns”*. DNS still resolves and port 443 is actively refused, which from one vantage point is indistinguishable from the host being down. Their spec asks clients to identify themselves and says access without it risks being treated as a crawler. `Http.Real` sends `Zedex/<version>` — the name and version and nothing else, the version from the package manager, which is why it takes a `Context` and why there is no second constructor that could go out without one — and `ZxInfo` paces itself because there is no quota to pace against. Neither is optional, and a bare `curl` against that host is how the address was lost in the first place. The interval was 500ms and is now **250ms** — measured, not guessed: the service answers a filecheck, a search and a record in 0.11–0.20s each, and a sweep is two API calls per game (the hash lookup hits for TOSEC-named files, so the name search is usually skipped), so at 500ms roughly two thirds of every game's API time was sleep and 800 games spent a quarter of an hour doing nothing. The block that motivated 500 was a burst with *no User-Agent*, which is a different failure from asking too often. If a 429 or 403 ever appears in the wild, this number is the first thing to put back — `refusalFor` maps both to `CLOSED`, which stops a run rather than letting it hammer on.
- **`PENTAGON` is a sibling of `ZXSPECTRUM` in ZXInfo's scheme, not a variant of it.** Filtering a search to Spectrum silently excludes the Pentagon demoscene, which is most of what arrives as `.trd` and `.scl`. Scraping identifies a file somebody already has, so it filters by *nothing* — every filter can only lose the right answer.
- **`GET /v3/metadata/` is the vocabulary, and guessing it was wrong.** It answers with every value ZXDB uses for `machinetype`, `genretype` and features, with a count each — 32 machine types over 39,666 entries. `Suggested`'s table was written from one collection until that call was possible, and it matched `"16"` inside **`ZX81 16K`**, offering a 16K Spectrum for the third commonest value in the database. Substring matching needs the refusals spelled out (`NOT_A_SPECTRUM`), and the list lives in `SuggestedTest` so both directions are asserted. `controls` is *not* in that reply — for the input vocabulary the offline dump at github.com/zxdb/ZXDB is the source. The reply's own keys are **plural** — `genretypes`, `machinetypes` — and a parser written against a remembered `genretype` finds nothing, silently: that is how the catalogue's Categories shelf shipped with zero shelves.
- **Ask ZXInfo for `mode=compact`, not `full`.** Measured on one game: 45,318 bytes against 10,286, and every field this app reads or stores is in compact and byte-identical — `full` adds 37 more it does not. Only `inspirationFor` and the other reverse relations are full-only. `tiny` is not an option: it has no `controls`.
- **A media scan is `physicalmedia`, not a folder of its own** — ES-DE's name for the photograph of the cassette or disk is exactly what ZXDB means by one. Only maps and advertisements needed folders this app invented, and they go **last** in `Artwork.PICTURE_FOLDERS`, which is a preference order as well as a gallery: the first that exists is what every row draws, and a game map is a poor thumbnail for a game that has a cover. Measured over ZXDB: media scan 11.8% of entries, game map 5.3%, advertisement 4.0%.
- **A ZXInfo record's paths are relative to two different hosts.** `/pub/` and `/zxdb/` are on `spectrumcomputing.co.uk`; `/zxscreens/` — every *rendered* loading screen — is on `zxinfo.dk/media` and 404s on the archive. Both appear inside the same `screens` array, so the array is no guide and the prefix is the only thing that decides. Until this was measured, every loading screen the provider offered was fetched from the wrong host and discarded as a 404, which looks exactly like a game that has none.
- **A manual is a PDF *or* a transcription**, and ZXDB has more of the second — 6,945 text files against 3,723 PDFs, so taking only the PDF meant no manual for most games that have one. Both live in `manuals/` and `Artwork.MANUAL_EXTENSIONS` resolves either, PDF first; `Manuals.open` picks the viewer by extension. The text one is shown by `InstructionsActivity` rather than handed out with `ACTION_VIEW`: not every phone has anything for `text/plain`, and the ones that do re-wrap it — these are hard-wrapped at ~78 columns with rules under the headings, so wrapping ruins them. Monospaced, never re-wrapped, text scaled so the author's line length fits.
- **ZXInfo renders `.scr` dumps itself**, so the plan's "nothing else can show these" was wrong for it: of 26 sampled records, all 15 with a dump also offered a rendered PNG and none offered a dump alone. `ScreenDump` is a fallback for a record that offers only the dump, not the main path — the rendered picture is preferred, and that ordering is deliberate.
- **`ImageView.getAccessibilityClassName()` returns `android.widget.ImageView` whatever you subclass it into** — so a UI Automator selector built from the subclass name finds nothing, which looks exactly like a screen that failed to draw. Match the framework class instead. And "no picture on screen" is not "the viewer closed": whatever is behind it is a launcher full of icons, every one an `ImageView` — ask the activity registry which activity is RESUMED.
- **A view that consumes touches takes the tap somebody else was listening for.** `MediaViewerActivity` closes on a tap; the zoom handler swallowed every event and shipped a picture with no way out but Back. `ZoomableImageView` answers `onSingleTapConfirmed` with `performClick()`, which costs the double-tap timeout before the viewer closes and is the only way to tell "the first tap of a zoom" from "done".
- **The ZXDB dump answers "how common is this?" for free** (github.com/zxdb/ZXDB, 27 MB zipped, MariaDB syntax — parse the `INSERT` tuples, no server needed). Its `entries` with a machine type number **39,666**, exactly the API's own total, which is how you know the parse is right. Series is tag type `S`, controls tag `J`, known errors note `E`, mod/inspired relations `m`/`i`. Measured: authors 63.6%, in-a-compilation 26.6%, price 23.7%, **controls 9.8%**, series 6.4%, known errors 0.34%. That controls figure is why the hand-edit screen is the main path for them and the scrape is the exception.
- **`offset=random` is not random per call** — two successive `/search?offset=random` requests returned the identical ten entries. Sampling with it measures nothing; use the dump.
- **A recorded reply is one the service actually sent.** A fixture written from memory pins the memory, not the service, and it passes — three separate defects on the catalogue branch hid behind one each: `genretype` for the reply's `genretypes`, a `doc_count` of 5,731 for a real 6,436, and `"format":"TZX"` for `Perfect tape (TZX)`. The last of those made **every entry in the database unimportable** while every test was green and two reviews approved it. Capture the reply, keep the capture, paste the value in; where a boundary value has to be invented, say in the fixture that it was.
- **ZXInfo's `format` is a human phrase, never a bare extension** — `Perfect tape (TZX)`, `Tape (TAP)`, `TR-DOS disk (SCL)`, `Game recording (RZX)`, and a bare `Picture` with no code in it at all. `ZxInfoCatalogue.formatOf` reads the parenthesised code and falls back to the path; `ZxInfo.extensionOf` next door says the same thing about the same vocabulary, and the two must not disagree. What decides whether Fuse can open a file is what is *inside* it, so `HeadOverHeels.tzx.zip` is a tzx.
- **A recording is in the entry's `additionalDownloads`, never in a release's `files`** — six captured, none the other way. Read only from the releases and `Pick.recording` is null for every entry there is. It lands in `Downloaded/Recordings` whatever the entry's genre says: the folder scheme answers "what kind of thing is this file", and a recording of Bomb Jack in Games is not Bomb Jack.
- **A search's `total` comes back as exactly 10000** — Elasticsearch's window cap against a real ~39,666. Right to page against, a lie to print, so a count is only shown below the cap.
- **An unrecognised zxart filter is ignored, not refused.** A guessed parameter name against zxart's search came back with all 58,032 entries — no error, no empty result, just every record, `responseStatus: success` — which reads as a search that matched everything rather than as a wrong parameter name. Built now, and the measurement held: eight names read exactly this way — `zxProdTitleSearch`, `zxProdTitle`, `zxProdTitleStart`, `zxProdMd5`, `zxReleaseMd5`, `zxProdImportId`, `zxProdWosId`, and `action:search` with `query:` — and the first of those is what this project's own earlier notes had recorded as the title search, so the very name reached for first was one of the eight that does nothing. `ZxartApi` keeps every filter and order name it sends as a constant with the date it was measured, for the same reason `/v3/metadata/`'s vocabulary above is a table rather than a guess: an unfamiliar-looking total is a wrong parameter, not a real answer, and a filter has to be checked against the service's own vocabulary before it is trusted to filter anything.
- **`types:zxProd,zxRelease` is documented by zxart's own author for fetching a prod with its releases together, and answers HTTP 500 regardless — with or without `action:filter`.** So a prod and its releases are two requests, never one, however inviting the documented shortcut looks; `Zxart.fetch` and `ZxartCatalogue.item` both pay for it separately. `ZxartApi.refusalFor`'s own comment states the wider lesson this forced: zxart answers a request it does not understand with an empty-bodied 500 exactly as it answers a real server fault with one, so a 500 on every call is this file's own bug and a 500 in a hundred is the network — the difference shows up in the log, not in which `Kind` gets thrown.
- **zxart's `limit:` is never left out.** Omit it and the service defaults to **1000** — a 1.18 MB reply for what was meant to be one page, measured by asking without it. `ZxartApi.Ask` always states one, for the same reason its own javadoc gives for fixing the order of every other segment: a builder that could send a request with one field missing is a builder that eventually will.
- **The order answers to `votes`, never to `rating`, on prods, music and pictures alike — even though the reply calls that very field `rating` on music and pictures.** `order:rating,desc` and `order:votesAmount,desc` are both ignored (control: the unfiltered list, byte-identical); only `order:votes,desc` changes the reply at all, and it does so on all three entities. `ZxartApi.ORDER_TOP` is `"votes,desc"` and stays that whichever entity it is asked against — a table per entity here would be a second way to get this wrong that nothing has tried yet.
- **`legalStatus` never says a zxart prod is available — it says nothing, or it says why not.** Over 1,000 prods: `unknown` 975, `forbidden` 21, `unreleased` 3, `recovered` 1 — the word "available" appears in none of them. Passed straight into `Item.availability` this would grey **every zxart row in the catalogue**, since `CatalogueAdapter.greyed` reads "stated, and not available" and `unknown` is stated. So `unknown` becomes **null** — nothing stated, nothing greyed — and the other three pass through verbatim as the row's own reason (`ZxartCatalogue.availabilityOf`).
- **A zxart prod's publisher cannot be resolved to a name, and it is not for want of trying.** A prod carries `publishersIds` and nothing that turns one into a name: `export:publisher` answers HTTP 500, `export:group` parses and answers nothing for a publisher id, and `export:author` — which does resolve an author id to a name — has no row for a publisher's. Comma-joining several ids into one filter was tried too and came back as a single row, so there is no batch call hiding behind the single-id one either. `ZxartCatalogue.itemFrom` answers null rather than guessing, and `Item.describe()` already skips whichever of year and publisher is unknown, so a zxart row reads "Head over Heels (1987)" with nothing dangling. Authors are a different story — `export:author/filter:authorId=` resolves cleanly — which is why the pane can name who made a tune or a picture but never who published a game.
- **zxart's `robots.txt` disallows every path this app touches, not just `/api`, and `ClaudeBot` by name with `Disallow: /`.** The full list is `/about/contact-us/`, `/simple`, **`/release`**, `/zxfile`, `/remote`, `/banner`, `/api`, `/zipItems`, **`/file`**, `/print`, `/redirect` (`review/zxart/robots.txt`) — and the two in bold are the ones the earlier version of this note missed: every inlay, advert, instruction and map url this app fetches is `/release/id:…`, and every game download is `/releasefile/…`, so *all* of it is under a disallowed prefix rather than only the lookups. The API is published, documented by the site's own author, and served happily to an identified client, and a person opening a shelf or scraping a game they already have is not a crawler — but the ZXInfo block above is the standing proof that a site can act on a stated preference whether or not the traffic technically deserved it. So: **250ms between requests, per host**, for the **API** (`ZxartApi.MINIMUM_INTERVAL_MS`, paced through `Pace.before("zxart.ee", ...)`); nothing fetched speculatively — no prefetch, no warming, no background sync, exactly a page when the grid reaches it and a thumbnail when its row is on screen; an identified `Zedex/<version>` User-Agent on every request (`Http.Real`, unconditionally); and a letter to the archive's own author describing all of that, written before the feature ships rather than after a block. **The letter is drafted, not sent** — `.superpowers/sdd/2026-08-14-zxart-integration/zxart-email-draft.md`, dated 2026-08-14, addressed to an email recovered from a quoted header in a blog comment rather than published on the site itself, worth a second look before it goes. Sending it is the maintainer's call, and the record says drafted until it is: claiming a letter went that did not is worse than not having written one.
  - **The media requests are not paced, and for zxart that is the same host as the API — a known gap, stated rather than glossed.** `Pace.before` is called from the three API clients only; `Thumbnails` deliberately does not pace and `Downloads` does not either, on an argument inherited from ZXInfo, where `api.zxinfo.dk` and the picture hosts are different addresses. zxart serves both from `zxart.ee`, so a thirty-row page is a burst of up to `Work`'s lane count (`max(4, cores)`) of concurrent unpaced requests at exactly the address the API waits 250ms between calls to. Not changed in the fix wave that found it, deliberately: what a page of thirty covers costs at the current lane count, against a paced alternative, is a measurement nobody has taken, and an interval picked without one trades a usable grid for a guess. Take the measurement first; `ZxartApi.MINIMUM_INTERVAL_MS`'s javadoc carries the same note where somebody changing the pacing will read it.
- **zxart's `language:` segment does not affect its search, though it changes almost everything else.** `filter:zxProdSearch=dizzy` under `language:eng` and under `language:rus` answered `totalAmount 189` both times, the same ten ids **in the same order**, the same ten titles — the replies differ in size only (12,441 bytes against 13,988) because `categoriesString` and the tags come back translated and the search path reads neither. So a client that reads only ids, titles and years can ask in whatever language suits it without changing which game it finds — which is why `Zxart` the scraper fixes its language to English forever while `ZxartCatalogue` the browsable archive asks in the person's own: the two are answering different questions, and only one of them is sensitive to the answer changing under it.
- **What a scrape writes must be language-stable even where browsing need not be.** `Facets` groups a collection by the exact strings a scrape stored in `Meta` — "built from the collection rather than from a fixed list", its own javadoc says, precisely so nothing unfamiliar is ever invented — which means a genre scraped once in one wording and once in another for the same real category silently becomes two facets, with `Merge`'s fill-gaps rule handing that bucket to whichever wording arrived first, permanently. This is the reason `Zxart.fetch` never varies by the device's own locale even though nothing stops the *catalogue* half from doing exactly that: a browsing person reads a translated label and moves on, but a written field has to agree with itself forever, on every phone it is ever read on again.
- **zxart's rendered picture is a PNG, and nothing about the reply says so.** Measured by fetching one: `zximages/id=2232;border=0;pal=srgb;type=standard;zoom=1` answers 200 with the PNG magic number in the body and **no `Content-Type` header at all** — and the url itself carries no extension either. So neither the transport nor the address says what the bytes are, and the **filename is the only thing that does**: `Imports.namedFrom` appends `.png` from the catalogue's own stated format when a download's url gives none, because `CataloguePane.openOutside` hands a document to another app with whatever `ContentResolver.getType()` answers, and SAF derives that from the **display name's** extension alone — a mime passed to `createDocument` is inert from the moment the document exists, re-derived from the name on every later query. This is also, not incidentally, why today's PDF imports already work through that same `application/octet-stream` call: their basename already ends `.pdf`, so the derived type was always right without anyone stating a mime at all.
- **A `<queries>` entry is needed for `mailto`, `application/pdf`, `text/plain`, `image/*` and `audio/*` — and not for `http`/`https`.** Measured both ways on an emulator with a browser and the YouTube app installed: `ACTION_VIEW` on an `https` url reached the same activity with the manifest entry present and with it removed and the app reinstalled, no `ActivityNotFoundException` either way — a web intent carries its own automatic exemption from package-visibility filtering that a bare scheme like `mailto` does not get. So the `https` entry zxart's video link added is not load-bearing the way the mailto and PDF entries above it are, and stays anyway, because Android's own documentation gives this exact shape as the canonical `<queries>` example and a future change to how the link opens (a chooser, an explicit availability check) is covered without the manifest needing to be revisited. The `ACTION_SENDTO` lesson does not transfer to a scheme the platform exempts.
- **A new `Meta` field costs eight places touched, not six.** The field itself, the copy constructor, the builder setter named for the field, `Field` plus its `get`/`set` cases, `Merge.of`, and `Metadata`'s writer and reader are the six anyone remembers going in — `videoLink` needed two more nobody had written down: two reflection walks that assert their own fixtures cover every field before asserting anything else (`BlendTest.everyMissingFieldIsSomethingLeftToGain` on the device tier, `MergeTest`'s own pair on the JVM tier), and `EditMetadataActivity.labelOf`, which without a case for the new field fell to the `default` and showed it labelled "Controls" — `INPUTS`' own fallback label, wrong for this field, on a screen no test looks at. Count eight before calling a new field done.
- **A catalogue's file urls are absolute, and some are on a host neither we nor ZXDB chose.** Measured over the dump: 4,941 of 153,959 download links start with `http`, 4,396 of them on archive.org — and for RZX recordings it is the majority, 4,047 of 5,462 rows. So `Catalogue.Download.url()` is absolute by contract and `urlFor` passes an `http…` path straight through; joining every path onto one base is the loading-screen mistake again.
- **ZXInfo's API drops every `additionalDownloads` row whose link is absolute, and that hides three quarters of all recordings.** This used to be recorded as a guess — "appears not to surface" — and is now measured, by comparing entries the dump says have a recording: **9 of 9** whose link is a relative ZXDB path came back with their RZX, **0 of 9** whose link is on archive.org did. Nothing else about those records is missing: Avenger (`0000351`) returns 26 other downloads in full and simply omits the one archive.org row the dump holds for it.
  - `mode=full` does not help and was tested for exactly this — the same four entries return the **identical** download list in both modes, at three to four times the bytes (Avenger 11,377 → 44,951, and not one extra download). Another reason the *Ask for `mode=compact`* rule above holds.
  - So `Pick.recording` and `ZxInfoCatalogue.recordings` can only ever offer the **1,353** entries whose recording is a relative path. **3,988** entries are archive.org-only and are unreachable through this catalogue, out of 5,385 entries with a recording at all — 13.58% of the 39,666, which is the "about 13.5%" `CatalogueView` already assumes.
  - Nothing is broken in this app: the passthrough is right by the dump, and would work if the row ever arrived. Reaching those recordings means getting the link from somewhere other than this API, which is a second source of truth and a decision rather than a patch. Left alone deliberately; do not "fix" it by guessing archive.org paths from a title.
  - The 44 entries holding both kinds of link are untested — they may well surface the relative one and hide the absolute, which would look like a recording that works.
- **A path under `/denied/` is a file the archive records and will not serve.** ZXDB carries the row, the size and the format for an entry whose distribution is denied, and the path it gives is under `/denied/` instead of `/pub/` or `/zxdb/` — and every one of those answers **404**, while every non-denied path on the same entry answers 200. Measured on 2026-08-14 after *Play the recording* reported *"That did not arrive."* for Atic Atac: `/denied/entries/0009305/AticAtac.rzx.zip` and its `.tzx.zip` both 404, `/zxdb/sinclair/entries/0009305/AticAtac.jpg` is served; same on 1942, 1943, 11-a-Side Soccer. Over 240 sampled entries the prefix appears only under an availability of `Distribution denied`, and all of those carry served paths too — so it marks the **file**, never the entry. `ZxInfoCatalogue.served()` drops them at the parse, which is the only place that needs to know: `Pick` then answers null instead of naming a 404, the pane offers no button rather than one that can only fail, and a format filter stops listing games whose only rzx or tzx nobody can have — an RZX shelf offering Atic Atac is how this was found. Do **not** drop the entry: the row is worth keeping (greyed, with the service's own reason), and its covers, maps, adverts and pokes are all served and all come through `ZxInfo` the scraper, which never sees a `/denied/` path. Two fixtures state the rule from both sides, `RECORD_WITH_RECORDING` (denied) and `RECORD_SERVED_RECORDING` (served) — the first used to pin "a recording is found at all", which it can no longer do, and a test asserting on a withheld file is a test asserting the app does the thing it must not.
- **Two facts a person keeps rather than scrapes: a play count and a completed flag.** Both are ES-DE's own gamelist elements (`<playcount>`, `<completed>`, lower case — EmulationStation's format, not ES-DE's invention), so a linked collection starts from what somebody has already played rather than from zero. Stored as **strings** like every other field, because the store writes by name through one helper and a second shape is a second thing for every reader to know; `Meta.plays()` and `Meta.isCompleted()` do the reading. `completed` has **three** states — `"true"`, `"false"`, absent — and only the first two are ever written by the tick box, so opening the editor and leaving cannot turn "nobody has said" into an explicit no. The count grows at `EmulatorActivity.gameOpened`, where all four ways in meet, through `Metadata.played`: it uses `but()` so the contributor list is untouched — marking it `USER` would make an ordinary game somebody played read as one they had corrected, which is what `Sweep.Only.NOT_SCRAPED` and the ES-DE link both turn on — and it makes a row for a game nobody has scraped, which stays unscraped because `Meta.isEsde()` answers true for no contributors at all. The three status filters are a fixed vocabulary (`Filters.STATUSES`) rather than values found in the collection, stored as stable keys and translated only for display, so a filter set in one language is the same filter in another; `Facets` still offers only the ones that would select something, which is the rule every other field follows.
- **The catalogue cannot be searched by file format, and the app filters instead.** Measured against the live service with a deliberate nonsense parameter as the control: an unknown parameter is **ignored, not refused** — `zzznonsense=xyz`, `format=rzx`, `filetype=rzx` and `downloadtype=rzx` all return the same 10,000 as no parameter at all. What *is* real: `machinetype`, `genretype`, `contenttype` (`HARDWARE` 843, `MAGAZINE` 0 — not a value), and `group=F&groupname=<feature>` (`AY Sound` 1,182; `groupname` **alone** is ignored, so it is the pair that filters). So `CatalogueView` keeps what arrives, which costs no request because **a row carries its own files**: a `mode=compact` search hit's `_source` holds `releases` and `additionalDownloads`, byte-identical to the record's — `/games` adds twenty-one *other* fields (`controls`, `series`), which is why the pane still fetches it. `itemFrom` used to discard them for list rows. The list of formats offered is `Types.openable()` and never a second list of its own. A filtered shelf cannot rely on the scroll listener to page it, and **"a page added a row" is not "the list can be scrolled"** — the second is what matters, and reading the first for it is how an RZX filter stopped at four rows against a live search that had ten in the pages it gave up on. Measured: page 1 of ten carried four matches, the chase ended there because *something* had arrived, four rows did not fill the screen, an unscrollable list emits no scroll event, and no page was ever asked for again — swiping did nothing, for good. So `deliver` keeps filling until there are `LOOKAHEAD` screenfuls below the last row showing — and **filling only until the list can be scrolled is the minimum, and the minimum is a treadmill**: that was the first cut, and it left a filtered shelf exactly one screen deep, so the first flick reached the bottom, bought one page and waited for it. Measured on a live TRD filter: 4.3% of entries, 1.3 rows per thirty-row page, ~0.45s a page — four rows and a wait, however hard somebody scrolls. `enoughBelow()` is one predicate for both the fill and the scroll trigger, measured off the layout manager (how many rows a screen holds is this device's business, not a constant). Two things that look like details and are not: the check is **posted**, since what is visible is what is laid out and the new rows are not laid out yet (inline it answers about the previous page, one page late for ever); and the bound is on the **whole fill**, not per page — resetting it on every page that brought something would let a one-in-thirty filter spend the budget again per row it found. That bound is counted in **entries read** (`SCAN`, 300) rather than pages asked for, because a sifting shelf asks for a bigger page and a bound in pages would silently triple the traffic the moment that size changed. A scroll is a person asking and starts a fresh budget; so does every new shelf (`restart`). The empty-page half of the chase stays synchronous: a page that added nothing cannot have changed whether the list scrolls, and going round through `post` would flash *Nothing here.* between every pair of pages. A shelf that sifts says so, through `Catalogue.Query.sifting()`, and `ZxInfoCatalogue` answers with `size=100` instead of 30 — **measured, and the win is round trips rather than bytes**: a page is 0.17–0.25s of network and this app waits 250ms between calls, so thirty entries cost ~0.45s and a hundred ~0.53s, which turns 300 entries from 4.5s into 1.6s for the same rows kept and roughly the same bytes (~2.5 KB an entry either way). The hint rides on `Query` precisely so a catalogue that has no notion of page size ignores it; an unfiltered shelf must never set it, since every row it fetches is drawn. **The size and the stride are one decision** — `offset` is a page number at this endpoint, so a shelf asking for 100 and counting `seenBefore` by 30 walks past its own end, one wasted paced request per fling. The two unpaged shelves (Surprise me, More like this) keep 30 whatever the query says: size is not a stride there but a statement of how big the shelf is. `CatalogueChaseTest` pins the view's end — fills past a screenful, gives up at the bound, sets the hint only when filtered — against a fake catalogue, since a test whose point is "keep asking for pages" must not ask the real host for ten of them per run; `ZxInfoCatalogueTest` pins the URL and the stride.
- **Two paging knobs under similar names, with opposite meanings: ZXInfo's `offset` is a *page* number and zxart's `start:` is an *item* offset.** So a ZXInfo shelf sends `offset=page` (measured: `size=30&offset=30` into a 153-row search came back **empty**, which a row offset cannot do — every shelf in the app stopped dead after its first thirty rows and read as a catalogue with thirty of everything), and a zxart shelf sends `start = page * size` (`ZxartApi.Ask.page`). Neither may ever be read as the other, in either direction, and both are asserted on the URL — `ZxInfoCatalogueTest` and `ZxartCatalogueTest` — because the failure is a 200 with plausible rows. Recorded as a bullet of its own because it used to be a coda on the end of the format-filter essay above, whose subject is `deliver`/`enoughBelow`/`SCAN`, where nobody looking for a paging fact would find it.
- **A fifth of the catalogue is not a program, and it is still worth fetching.** 1,570 books, 1,819 electronic magazines, 1,147 hardware entries — counted from the service's own `/metadata/`. Their file is a PDF sitting in the record one tap away, and the app's whole answer used to be *"Nothing here the Spectrum can open."* `Pick.otherFile` answers with the best non-game, non-recording file (a picture goes **last** — a book's cover is not the book, and both are on the same entry), and `Imports.document` brings it in: the same `Downloaded/<kind>/` folder as everything else, with `Keep.WHATEVER_ARRIVED` in place of the openable-only filter that `unzip` and the not-a-zip fallback both apply. That filter is why the first cut still failed with *"nothing inside this app can open"* — offering the file and importing it are two layers and both were built around the machine. The pane then offers **Open** rather than Play, handing it to the phone with the mime the *provider* states rather than one guessed from the name; `<queries>` declares `application/pdf` and `image/*`, without which Android 11+ hides every viewer and the hand-over resolves to nothing. `Imports.describe` is skipped for these: the row would be a PDF in `Downloaded/Magazines`, which nothing in the library draws.
- **Grey a row only on a *stated* unavailability** — and that is `CatalogueAdapter.greyed`, not `Item.available()`. Two questions, two predicates: `available()` answers "is there definitely something to download" and so reads an absent `availability` as false, which is right there and wrong for a row — a live record omits the field entirely on a 2024 release, and greying by `available()` tells somebody a game they can have is missing, giving no reason, because a field was absent. `greyed` asks whether the service *said* something and it was not "Available". `available()` matches the one good word rather than listing the bad ones, since a vocabulary that grows must not silently start reading as available.
- **The content folder was granted read-only until the catalogue needed to write to it.** `createDocument` throws, and `Storage.keepAccessTo` swallows the refusal, so an import does nothing and says nothing. A grant cannot be widened in place either — `takePersistableUriPermission` only ever adds what the *picker's own result* already carried, so the folder has to be picked again. `Tree.canWrite` reads the persisted list (matching on the tree's document id, not `Uri.equals` — the two are never equal), and `CataloguePane` asks on the spot, names the folder, opens the picker at it with `EXTRA_INITIAL_URI`, and resumes the import that prompted the ask.
- **SAF's uniqueness is the document id, not the display name.** `createDocument` over a name already there cheerfully makes `Games (1)`, which is how a collection acquires four of everything and how somebody concludes the first import failed. Find before you create (`Tree.find`).
- **A sweep's downloads run on a thread of their own** (`Backlog`), because the pictures come from hosts nobody paces and the facts come from an API this app deliberately waits between calls to. Fetched in line, the two queue behind each other: the sweep downloads a cover, then sleeps before the next game's first request, having had nothing to do during the sleep and something to do the whole time — measured, the two halves are about the same size. **One** thread, so two games' downloads never overlap each other and the file hosts see exactly the traffic they saw before. What it costs: a media host's refusal used to land in that game's failures where `Sweep` could drop the source (a spent ScreenScraper allowance is the case that matters); it now arrives at the next game boundary through `Backlog.refusals` — one game late, never lost, and quota is mostly seen from the counters in every reply anyway. `Result.installed` is 0 for every game under a `Backlog` by contract, and `Sweep` counts what landed once, from `drain()`.
- **`Pace` counts per host, not per object** — two objects each waiting 500ms and neither waiting for the other halve the real spacing exactly as the traffic doubles, against an address that blocks on behaviour patterns rather than on a published limit. Static state, deliberately: there is one network. The lock reserves the slot and is released *before* the sleep — holding it across the sleep paces every host through one queue, which is the per-instance bug again wearing a different hat.
- **A `Catalogue.Page` carries sub-shelves as well as items.** That is how a category tree and an A–Z fit through a seam with a method for neither: a shelf that has to fetch its own children declares one shelf and yields the rest when it is opened, which keeps `shelves()` requestless and callable while the tab is being built. A-Z needs no request at all — twenty-six letters are twenty-six sub-shelves.
- **A pad direction often arrives as a hat axis, not a key** — which Android turns into no focus move at all, so `onGenericMotionEvent` has to keep claiming pad input and move the focus itself (`padCursor.motion(event)`; literal `KeyEvent`s are `dispatchKeyEvent`'s own, via `padCursor.key(event)`). Falling through to the view tree looks like the tidier fix and leaves the D-pad dead.
- **The scraper credentials are in the APK and cannot be hidden there.** `aapt2 dump resources` prints them with no decompiler; R8 leaves resource values alone, a constant stays in the dex, a `.so` stays in `strings`, and encrypting ships the key. They are sealed (`Secrets`) only so they are not *greppable*, and the real mitigation is the optional per-user account. Do not reopen this.
- **`FuseNative.machineIds()` is empty until Fuse is running; `joystickTypeNames()` is not.** A test that reads the first and skips on empty reports "OK" having asserted nothing — which is how `SuggestedContractTest` passed while a mapping pointed at an id Fuse does not have. Launch the emulator first, then *assert* the array rather than assuming it.
- **Fuse has no joystick called the keyboard.** Its eight are None, Cursor, Kempston, Sinclair 1/2, Timex 1/2, Fuller; the pad's keyboard mode is *ours*, `Controls.JOYSTICK_KEYBOARD` (1000), appended after Fuse's list everywhere somebody picks one. Looking it up by name in `joystickTypeNames()` finds nothing and never will — how the setup dialog shipped with the option missing while the code that built it read correctly. Choose an interface through `ControlsUi.chooseJoystickType`: the setting, Fuse and the pad's layout are three things, and it is all three or none.
- **The metadata store does not read itself.** `Metadata.forPath` answers out of a cache that only `ensureLoaded`/`refresh` fills, and neither may run on the UI thread — so a game opened without the library having run first in that process finds an empty store and reads as unscraped, silently. `clear()` leaves the cache non-null and empty, so an `ensureLoaded` after it does nothing.
- **A row has contributors, not an owner.** `Meta.source` is a comma-joined list, and three predicates read it, each a different question: `isEsde()` is true only when ES-DE is the *sole* contributor — a link may replace a row only when nothing else has touched it since; `isMine()` is true when `"user"` is *among* the contributors, however many others are; `Sweep.Only.NOT_SCRAPED` is `isEsde() || isMine()` — true when nothing has scraped the row *or* a person has since hand-edited it, and the second half counts even when a provider's name is also on the row (`meta.isMine()` asks whether `user` is among the contributors, not whether it is the only one). A row ZXInfo scraped and a person then corrected is still "not scraped" and is re-offered — correctly, since fill-gaps-only means a re-scrape can only add to it, never undo the correction. Confusing "the only one" with "one of them" answers the wrong question for whichever predicate borrowed the other one's test.
- **Fill gaps, never overwrite.** `Merge.of(base, addition)` is the whole rule for combining what two sources say about one game: a null or empty field is taken from the addition, anything else stays. This is what makes several sources safe — there is no rule *per field* to get backwards, because the priority order already decided who answers first — and it is why the hand-edit confirmation dialog is gone: a typed value is never null, so a scrape cannot overwrite it, and the dialog's question no longer has an unsafe answer to guard against.
- **A sweep asks only for the folders that are empty; a one-game scrape asks for everything and stages it.** `Blend.Media.FILL_GAPS` never requests a cover that already exists, which is the whole of "do not replace artwork we have" and also why it costs no request. `OFFER_ALTERNATIVES` fetches every wanted folder from every source into `<media>/.staging/<folder>/<source>/`, because the sheet cannot offer a choice it did not download — contested or not is only knowable once the file is actually on disk. **Contested is a question about the folder, not about the user's own file**: asking only "do these bytes differ from the ones already there" meant a first scrape of a game with no media — the commonest scrape there is — silently took whichever source came first in the order and threw the other's cover away unseen. `Blend.Result.anythingContested` compares the offers with each other as well, and identical bytes are still not a question either way (two services carrying the same scan is common).
- **Installing a picture deletes the other extensions for that game and folder.** `Artwork` resolves png before jpg, so a newly chosen `covers/X.jpg` written beside an untouched `covers/X.png` leaves the png on screen — the choice looks exactly like a choice that did nothing. `Blend.commit` calls `Artwork.removeOthers` after every install for this reason.
- **The staging area is cleared on the way in, not on the way out.** `Blend.run` calls `Artwork.clearStaging` before asking the first source, because a run killed mid-flight — the activity gone, the process gone, Back pressed — never reaches its own cleanup, and last run's leftover would be offered as though this run had fetched it.
- **A refusal belongs to the source that made it, not to the run.** A spent ScreenScraper quota is every remaining game for ScreenScraper and nothing at all for ZXInfo, which has no quota to spend — `Sweep.dropTheSpent`/`drop` remove only that source, and the run stops when no source is left standing, not on the first one to refuse.
- **`Scrape.apply` is the catalogue's alone now — do not point it at `Scrapers.enabled`.** Every other caller merges through `Blend.run`; `Imports.describe` still calls `apply` directly because a catalogue item's id is certain against the service that issued it and meaningless to any other — handing it to whichever source happens to be first in the user's order is a coincidence, not a lookup, and can describe a game with a different service's answer under the same number.
- **A worker thread must not block indefinitely on a dialog belonging to an activity that can vanish.** `ScrapeOneGame.askOnTheUiThread` polls `answered.await(200ms)` in a loop that checks `isFinishing()`/`isDestroyed()`, and the posted lambda checks the same before building the dialog at all — destroying the library while the per-source chooser was up used to park the `Work.alone` thread forever, holding a destroyed `Activity`. This is the *opposite* of `Sweep.Watcher.chooseFrom`'s own rule — block until answered, deliberately no timeout, because a sweep can run for twenty minutes unattended and skipping a game nobody was looking at is worse than waiting — and the difference is the point, not an inconsistency: a sweep has no activity to vanish out from under it, a per-game dialog does. Copying one pattern onto the other reintroduces whichever bug that context does not have.
- **Every way of opening a game meets at `Media.Host.opened`** — a file manager's hand-over, the library, the picker, *Open recent…*. A hook hung on `ACTION_VIEW` covers one of the four, and `EmulatorActivity.gameOpened` is where the other three arrive too.

## Building

Native first, then Gradle. Gradle only packages the prebuilt `.so`, so **changing C code and running `adb install` without `./gradlew assembleDebug` in between installs the old library**.

```sh
./scripts/build-native.sh                 # both ABIs, ~90s cold
ABIS=x86_64 ./scripts/build-native.sh     # one ABI while iterating
env JAVA_HOME=/opt/android-studio/jbr ./gradlew assembleDebug
adb install -r app/build/outputs/apk/debug/app-debug.apk
```

`JAVA_HOME` is needed whenever the default JDK is newer than 21.

`app/src/main/assets/fuse/` is staged by the same script and is not in git — nothing in the app reads it any more, so a tree without it still builds and runs; `./scripts/build-native.sh` puts it back.

## Tests

`app/src/androidTest` — UI Automator. Run one class while iterating; the whole suite only for refactors or large features.

```sh
env JAVA_HOME=/opt/android-studio/jbr ./gradlew connectedDebugAndroidTest \
    -Pandroid.testInstrumentationRunnerArguments.class=dev.ldlab.zedex.CaptureTest
```

Things learned the hard way, all recorded in the tests' own comments:

- **Run instrumentation on an emulator, not the tablet** — MIUI refuses Gradle's install with `INSTALL_FAILED_USER_RESTRICTED` unless *Install via USB* is on, and `connectedAndroidTest` **uninstalls first**, leaving no app and no way back without touching the phone. `adb install -r` + `am instrument` avoids the uninstall.
- **`Emulator.useDataFolder()` wants ROMs in `/sdcard/Download/Spectrum/roms`** — without them every test in the class fails before it can be skipped. `adb push roms/*.rom` puts it back.
- **A test sets the world it needs; it must not inherit the bench's** — the machine, the second screen, the orientation, the **display it comes up on**, and every setting it depends on. A bench left configured for the last thing worked on by hand is the normal case, not the exception.
  - **The display has to be said, and then checked.** An AVD with a second display hands the activity to whichever one last had focus, and the task stays there across launches; screenshots and taps always mean the default display, so `borderColour()` reads the other screen's launcher — white, where green was wanted. Nothing earlier can catch it: the accessibility tree spans every display, so the keyboard is found wherever it is and the launch reads as a success. `Emulator.launch()` pins it with `ActivityOptions.setLaunchDisplayId` and asserts it landed. This failed on `main` too — latent in the harness, exposed by a bench with two displays.
  - The same shape from the other side: `secondScreen` left on cost ten of thirty-eight, all reading *nothing on screen says Controls* — the panel is a `Presentation` on display 9 and UI Automator taps display 0, so the taps landed nowhere near the app.
  - **Wait for the condition, never for a duration.** A filter does not land when its sheet closes: `load()` walks the whole content tree through the documents provider off the UI thread, and how long that takes depends on the tree, the provider's caches and what else the device has been doing. `FilterTest` sampled the row count after a 400ms sleep — it passed alone and failed behind three emulator classes, reading the pre-filter count and reporting it as a filter that changed nothing. `awaitRowCount` polls until the count says something the caller will believe, and the caller's own assertion still reports the failure.
  - **A skip must turn on a fact, never on a wait.** `NewDiskTest` decided "the ROMs are missing" from what the screen said three seconds after a machine change, so a machine that had not finished changing skipped the whole test — silently, in twenty seconds, having formatted nothing and reported OK. It skipped and ran alternately on identical code. The skip now asks whether the ROM file exists, which no timing changes, and the interface appearing is an `assertTrue`. A real run takes about four minutes; anything near twenty seconds did nothing.
  - **A picker left open by hand outlives `am force-stop`.** It belongs to another package, so stopping the app does not touch it, and the next launch comes up behind it — after which every reading is of the wrong screen and the symptom is a key that is not on the keyboard. Cost an hour of bisecting builds for a regression that was not there. `Screen.assertHere()` now fails when nothing of ours is resumed and says what to do: `adb shell am force-stop com.google.android.documentsui`.
  - **A killed run leaves its fixtures behind, and MediaStore does not overwrite.** Asked for a name that is taken it makes `uitest-recent (1).tap`, so the next run fails on what reads like a naming bug in the app. Clear leftovers on the way *in* — `RecentsTest.dropAnyLeftOver` — since a run stopped by hand never reaches its `@After`.
  - Restore whatever you turn off afterwards — it is the user's device, and the setting they left on is the one they were using.
- **Sample the picture, not a view's bounds** — `borderColour()` computes the 4:3 quad the way the renderer does; the window's corner is wrong once the bar takes a strip, the `SurfaceView`'s bounds are wrong sideways.
- **Ask for portrait, not for natural** — on a tablet natural *is* landscape.
- Instrumentation runs **inside the app's process**, so `am force-stop` kills the test with it.
- **A run uninstalls the app afterwards**, wiping prefs and storage permission — the next launch forgets the data folder. See *Device setup*.
- **`connectedDebugAndroidTest` uninstalls the app *before* running too, which wipes the SAF content-folder grant** — and that grant can only be restored by hand, through the app's own folder picker; nothing on a command line can hand it back. Several tests are guarded by an `assumeTrue` on it, so once the grant is gone they skip silently and print `OK` having asserted nothing. Install once by hand instead and drive the already-installed build directly:
  ```sh
  env JAVA_HOME=/opt/android-studio/jbr ./gradlew assembleDebug assembleDebugAndroidTest
  adb install -r app/build/outputs/apk/debug/app-debug.apk
  adb install -r app/build/outputs/apk/androidTest/debug/app-debug-androidTest.apk
  adb shell am instrument -w -e class <FULLY.QUALIFIED.TestClass> \
      dev.ldlab.zedex.debug.test/androidx.test.runner.AndroidJUnitRunner
  ```
  `OK (n tests)` prints identically for a real pass and for every test in the class skipping on that same `assumeTrue` — read the count against the number of `@Test` methods, or add `-r` to `am instrument`, which reports `ASSUMPTION_FAILURE` by name instead of folding it into `OK`.
- `UiObject2.longClick()` holds the platform long-press timeout, the same 400ms the keyboard latches at — hold with a zero-length swipe instead.
- **A fresh install comes up on the first-run panel, not the machine** — it sits over the quick bar, so every menu test fails with *the ☰ button never appeared* (fifteen of thirty-four did once); since Gradle uninstalls first, **every** run starts this way. `Emulator.launch()` answers with `R.string.setup_start`, not English, since the app has languages now.
- **Read the *first* failure, not the count** — one flake cascades into every later class failing the same way.
- **☰ fades out after three seconds** — `Emulator.menu()` taps the picture to reveal it every time, first.
- **A BASIC program belongs on a tape, not the keyboard** — `TapeProgram` writes a real `.tap`; typing costs 150ms a character. Exception: a machine not at a BASIC prompt, where autoloading types `LOAD ""` itself.
- The emulated screen cannot be read, but a **screenshot of the device** can — have the test program report what it saw in the border colour (`Emulator.borderColour()`).
- **Do not drive the picker; make a document instead** — a `MediaStore` `content://` URI plus `ACTION_VIEW` takes the same path a file manager's hand-over does, the only way to reach `Media.stage()`. `Emulator.open()` calls Fuse directly and misses it.
- **UI Automator switches accessibility on**, so anything guarded by `AccessibilityManager.isEnabled()` behaves differently under test — a crash on latching a shift once shipped for exactly this reason.
- **At a BASIC prompt the first key of a line is a keyword** — `B` gives `BORDER`; typing the six letters gives `BORDER ORDER` and a syntax error.
- **Poke above RAMTOP** — the printer buffer at 23296 is only free on a 48K; on a 128 the byte is gone before the next `PEEK` sees it. `CLEAR` down to 32767 and use 32768.
- **`By.desc` is an exact match** — card buttons are described `Rename "Tujad"`, quotes and all, so `find()` uses `descContains`.
- **A row that was a dialog is a page now** — the button commits by its own name (*Save as…*, *Delete*), and there is no OK.

```sh
# ...and dev.ldlab.zedex.debug for a build straight off the bench.
adb shell appops set dev.ldlab.zedex MANAGE_EXTERNAL_STORAGE allow
adb shell "run-as dev.ldlab.zedex mkdir -p shared_prefs"
# shared_prefs/fuse.xml:
#   <string name="statesRoot">/storage/emulated/0/Download/Spectrum</string>
```

Use the canonical `/storage/emulated/0/...`; `/sdcard` is a symlink and string comparisons against `getExternalStorageDirectory()` will not match it.

**`MANAGE_EXTERNAL_STORAGE` is a uid op, and taking it away needs `--uid`.** `appops set <pkg> ... deny` writes a package line that `Environment.isExternalStorageManager()` ignores once the uid has been allowed — `appops get` shows both, the uid one first, and that is the one that counts. Revoke with `appops set --uid <pkg> MANAGE_EXTERNAL_STORAGE deny`. The package must be installed for either: `appops` on an absent one says *No UID for …*.

## Driving the app from a terminal

A plain `adb shell input keyevent KEYCODE_A` reaches the emulator and types an `a` — but nothing shifted, no keyword, and `input text` does nothing at all. Two helpers:

```sh
scripts/ui-tap.py list                    # what is on screen
scripts/ui-tap.py "Media" "Beta Disk A" "Save…"
scripts/ui-type.py 'randomize usr 15616' ENTER
scripts/ui-type.py CS+SS SS+0 ' ' '"test"' ENTER   # extended mode: FORMAT
```

`ui-type.py` asks the view hierarchy where each key is, by the name the Spectrum gives it, so it types on any of the four keyboards. Neither script can type on the **Android keyboard** skin — the phone's own IME, which Gboard hides on an AVD that reports a hardware keyboard; `adb shell settings put secure show_ime_with_hard_keyboard 1` brings them back. **After switching skins, `ui-tap.py` still reports the old skin's key names** — UI Automator caches the window's tree. Relaunch first.

Both address things by name, never by coordinate. ☰ has **pages**, so a path is several names deep: `"Machine" "Change machine" "Scorpion"`. The quick bar fades after three seconds, so tap the picture first to bring it back.

**Test on the hardware when there is any** — both scripts pick a real phone or tablet over an emulator (`ANDROID_SERIAL` overrides); prefer it for layout, since the two costliest bugs (keys vanishing, a joystick too low to hold) were a tablet's geometry and dpi that an emulator agreed the wrong way about. Pass `-s`, since a bare `adb shell` with both attached fails with *more than one device*.

**Check what is in front of the app before believing a measurement** — a settings page or file picker taking focus turns "the buttons are gone" into a reading of the wrong screen. Assert `ResumedActivity` is `EmulatorActivity`, or screenshot, before trusting a count.

**Testing a second display:** `screencap -d` wants the **SurfaceFlinger** id from `adb shell dumpsys SurfaceFlinger --display-id`, not the Android display id (it changes on reconfiguration); `adb shell input -d <android id> tap X Y` uses the **Android** id; `am start --display 0 …` pins an activity to the main screen or it opens on the panel instead.

**`ui-tap.py` caches the view tree across an orientation change** and hands back stale coordinates, which reads as an app bug — tap from a fresh screenshot when something looks wrong.

**Do not drive the device from two places at once** — two agents, or an agent and a person, tapping the same emulator make each other's results untrustworthy.

## Where things live

`FuseNative` and `EmulatorActivity` stay in `dev.ldlab.zedex` and cannot move: the native side exports 71 `Java_dev_ldlab_zedex_FuseNative_*` symbols — 57 in `android_bridge.c`, 12 in `android_state.c`, 2 in `android_window.c` — and does a `FindClass` on that path, and the activity is addressed as `dev.ldlab.zedex/.EmulatorActivity` by `am start` in the scripts and docs. Everything else is in a layer — `machine`, `input`, `storage`, `cheats`, `media`, `view`, `menu`, `screen`; see *How the code is laid out* in `docs/INTERNALS.md`. Adding an activity means the manifest gets `.screen.Name`.

A member another layer needs has to be `public`; package-private stops at the boundary.

## Refactoring this codebase

- **Build collaborators in `onCreate`, never as field initialisers** — those run first and are handed a null `preferences`. It compiles.
- **A `Host` interface wider than about four methods means the seam is wrong** — "Move the menus out" needed fifteen, so the menus stayed; pass a real collaborator instead (`ControlsUi` holds `EmulatorLayout`).
- **Extract first, move into packages after** — every cross-package reference has to become `public`; pay for it once.
- **Never script the `public` widening by indentation** — eight spaces is a method body at a top-level class and a member inside a nested type. Let the compiler name what is invisible; guessing cost an hour and a `git reset --hard`.
- **When a class leaves, read what it left behind** — comments do not move with the code; eleven were lying after this refactor, the worst a fifteen-line explanation stranded above an unrelated constant.
